# 2× RTX 2080 Ti 22G（sm_75）本地大模型部署与调优记录

> 目标硬件：2× RTX 2080 Ti 22GB（改装卡，NVLink NV2，PCIe 3.0 x8/卡）+ Ryzen 7 3700X + 93GB DDR4-2667 + KIOXIA BG5 NVMe。

> 上游版本：Maya v1.1.46（含我们提交并合并的 loop guard 修复 #704）。

## 3. GLM-5.3 Maya-S24 调优

### 3.1 有效项（逐项重启实测）

| 项 | 效果 |
|---|---|
| `MAYA_GLM_DUAL_PREFILL=1`（NVLink） | 1.7K 填充 201→301（+50%），5.8K 375→453（+21%） |
| `--kv int8` | decode +7.6% |
| `--expert-cache-per-layer` | decode +9%（29.4→31.7），命中 78.5%→80.8% |
| 功耗墙 160W→220W | 填充 +5~9%（160W 时实测顶到 163W 被卡） |
| `MAYA_GLM_MISS_SKIP_W=0.12` + `_FROM=23` | **decode 28.7→32.1（+12%）**；CPU lane 52→32 专家/token，PCIe 取用 22.7→12.2/token，命中 79.4%→87.7% |
| `MAYA_GLM_SPEC_CANCEL=1`、`SPEC_SAMPLE=1` | 采样场景 +2% |
| `MAYA_GLM_USAGE=/path/expert-usage.txt` | 在线学习路由，跨重启生效；命中率随使用提升到 85–91% |
| `reasoning_effort: max→high` | 非吞吐，但首字延迟 −46%（同 3 题 274s→147s） |
| `MAYA_GLM_SLOT_KEEP=1` | 会话跨重启保留，重启不再重读 |
| **`MAYA_GLM_DEFER_CPU=2`**（PR #722） | **decode 31.3→33.8（+8.0%）**，prefill 不变；有损 |

### 3.2 无效/有害（已回滚）

| 尝试 | 结果 |
|---|---|
| `PREFILL_MIN_CHUNKS=2/4` | 1.7K 掉到 240/139（切块破坏 DUAL_PREFILL 单 chunk 路径） |
| `PRESTAGE=160` | 1.7K 169（借走池尾，驻留专家 2543→218） |
| `PREFILL_SUB=1024` | 无变化 |
| `PREFILL_CPU=0` | 243/416/520（CPU 分担其实在帮忙） |
| `--vram-reserve-mib 400` | +88 槽但引擎警告 "requests may stall"，无速度收益 |
| `MAYA_GLM_PROMOTE_MIN=6` | 27.5（−13%），命中掉到 75% |
| `--parallel 2` | 单流 25.2，2 路聚合 13.4（远低于串行 27） |
| `--prefill 16384` + `PREFILL_KEEP=11` | 13K 填充 602→477（借 3.1–3.8GB 池尾） |
| #630 route-one PR | 28.9，无变化 |
| `MAYA_GLM_MLA_ATTN2` / `DSA_SCORE2` 标签 | sm75 上不生效（日志仍 original kernels） |
| 25 个请求训练的离线 profile | 27.2 vs 29.0（样本太少，过拟合） |

### 3.3 关键洞察

- **每 token 368 次专家激活（46 层×8）**，其中约 73 次要"跨内存墙"：~52 个由 CPU lane 算，~21 个走 PCIe。
- 显存 5,148 槽 / 12,384 专家（41.6%）；每 token 从内存读约 17–24 个专家（每个 6.9MB）。
- 三条硬瓶颈：显存容量、PCIe 3.0 x8（~6.6GB/s/卡）、DDR4-2667 双通道（31GB/s）。
- CPU lane 已吃 23/31 GB/s 内存带宽，**加 CPU 频率无效，加带宽才有效**。

## 4. DeepSeek-V4.1 Maya-XS 调优（收益最大）

### 4.1 调优阶梯（每步重启实测，唯一 nonce prompt）

| 步骤 | 配置 | Decode | Prefill 13K |
|---|---|---:|---:|
| 0 | 默认（mmap auto，无草稿器） | 11.7 | 305 |
| 1 | + DSpark + 视觉塔 | 15.4 | 369 |
| 2 | **`--mmap-experts off`**（80GB 专家进 pinned RAM）+ `DS4_STREAM_ZC/WIN`、`DS4_LAND` | 19.3 | 364 |
| 3 | **`MAYA_DS4_TP_GGUF_UNEVEN=1`**（5+4 块强制 TP2 成形） | 18.3 | 468 |
| 4 | `--experts 4`（有损，top-4/384 重归一化） | 27.7 | 483 |
| 5 | `MAYA_DS4_AR2=1`（all-reduce 单次启动） | 28.2 | 506 |
| 6 | `--max-context 262144` | 27.3 | 508 |
| 7 | **`DS4_TP_SHARES=4,5`**（槽位 3,048→3,794） | 30.1 | 560 |
| 8 | `--prefill-chunk 8192`（默认 4096） | 30.3 | **641** |
| 9 | `--reserve-mib 300`（默认 600，+204 槽） | 31.0 | 652 |
| 10 | `"gpu": [1,0]`（lead 避开桌面占用卡） | 30.3 | 641 |
| 11 | **PR #695：IQ1_S CPU 行向量化解码（逐位一致）** | **41.6** | **665** |

### 4.2 最终配置

```json
{
  "gpu": [1, 0],
  "port": 8000, "host": "0.0.0.0", "api_key": "CHANGE_ME",
  "args": ["--pack", "<Maya-XS>/maya-ds4", "--max-context", "262144", "--tp", "2",
           "--dspark", "on", "--mmap-experts", "off", "--experts", "4",
           "--reserve-mib", "300", "--prefill-chunk", "8192"],
  "env": {
    "DS4_STREAM_ZC": "1", "DS4_STREAM_WIN": "1", "DS4_LAND": "1",
    "MAYA_DS4_TP_GGUF_UNEVEN": "1", "MAYA_DS4_AR2": "1",
    "DS4_TP_SHARES": "4,5", "MAYA_DS4_SLOT_KEEP": "1"
  }
}
```

启动约 6–7 分钟（80GB 专家复制进 pinned RAM）。

### 4.3 无效/有害

| 尝试 | 结果 |
|---|---|
| `DS4_FLOW_TP=1` + `TP_BORROW=1` + `chunk 16384` | 13K 560→388 |
| `DS4_RING_MB=auto` | 13K 641→403 |
| `--reserve-mib 100` | **首次请求引擎退出**（CUDA0 仅 2MiB） |
| `DS4_TP_SHARES=3,6` | 517（CUDA1 挤满） |
| `DS4_DRAFT_GPU=1` / `DS4_DRAFT_DEV=1` | 主从互换，decode 25.7–26.0 |
| `DS4_ENGRAM_CACHE_MB=4096` + PREFETCH | 13K +2%，decode −1，内存更紧 |
| `--parallel 2` | 单流 −4%，2 路聚合 25.2（专家抢缓存） |

### 4.4 质量（10 题固定集）

| 配置 | 正确率 |
|---|---|
| `--experts 6` | **10/10** |
| `--experts 5` | 未测（decode 23.7） |
| `--experts 4` | **9/10**（唯一差异是正则写成 `[1][3-9]\d{9}`，实际有效；1234×5678 它做对了，GLM 做错） |

### 4.5 关键洞察

- 277GB 里 **161GB 是 Engram 表（常驻 SSD，每 token 读几 KB）**，真正驻留约 116GB；93GB 内存装不下 → 1,413 个专家读盘。
- **TP2 默认会退化成层切分**（`n_ff 2304` 无法按 256 值块二分），强制 5+4 后 prefill +29%。
- decode 是 **CPU lane + 内存带宽** 受限；prefill 是 **层内计算 + 两半区串行** 受限（copy lane 占墙钟 87%，但真正传输只占 26%）。
- 两卡显存不平衡（lead 104MiB 空闲 / 第二卡 1.5–2GB）是 TP 槽位取整 + head/草稿器归属决定的，所有调参尝试都失败（见 issue #734）。

### 本机踩过的坑

1. **loop guard 折叠历史 → 12.6 万 token 全量重读（~2 分钟）**：已用补丁修复（长对话 >32000 字符不折叠）。
2. **`SLOT_KEEP` 打开后，重复 prompt 会命中会话槽**，测 prefill 必须加随机 nonce，否则得到假数据（0.08 秒）。
3. **图片不会导致重填**（实测只读 34 token）；GLM/DeepSeek 两条图片路径都正常。
4. **桌面会话占用主卡 ~212MB**：用 `"gpu": [1,0]` 让 lead 避开，白捡 144 个专家槽（+3.6%）。
5. **`stop_*.sh` 的 pgrep 兜底会误杀调用它的 shell**：已加 `ps -o comm=` 过滤，只杀 python 进程。

## 8. 工作流（本机约定）

固定在这个分支上工作：**`2080ti22GX2`**（= 上游 main + 本文档 + 配置/脚本备份）。

```
1. docs/2080ti22gx2/sync.sh --check     看上游有哪些新提交
2. 挑有价值的：停服务 → git checkout 该提交 → 重新编译 → 跑 bench
3. 结果记入 docs/2080ti22gx2/BENCHLOG.md（基线 + 每次验证）
4. decode/prefill 掉 >3% 就不合；±3% 内按需；>3% 提升才更新基线
5. 有用就 git merge 进本分支 → git push fork 2080ti22GX2
```

- 分支只加文件、不改上游代码，合并永不冲突。
- 我们自己的修复走 `git checkout -b fix/xxx main` → PR；合并后主干会自动带回本分支。
- 配置改动（`maya-*.json` 被 gitignore）要手动同步到 `docs/2080ti22gx2/` 并去掉 `api_key`。
