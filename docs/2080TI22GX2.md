### 3.3 关键洞察

- **每 token 368 次专家激活（46 层×8）**，其中约 73 次要"跨内存墙"：~52 个由 CPU lane 算，~21 个走 PCIe。
- 显存 5,148 槽 / 12,384 专家（41.6%）；每 token 从内存读约 17–24 个专家（每个 6.9MB）。
- 三条硬瓶颈：显存容量、PCIe 3.0 x8（~6.6GB/s/卡）、DDR4-2667 双通道（31GB/s）。
- CPU lane 已吃 23/31 GB/s 内存带宽，**加 CPU 频率无效，加带宽才有效**。

### 4.5 AR2=2：prompt 的 all-reduce 走 FP16 线上（13K prefill +10%）

`MAYA_DS4_AR2` 是上游 **PR #513**（作者 Josef Gattermayer / @pepuscz，2026-10-27）引入的、DeepSeek TP2 在 **prefill** 阶段的 all-reduce 路径（`docs/SETTINGS.md` 第 1172 行，默认 `0`）：

| 值 | 做什么 |
|---|---|
| `0` | 关闭（默认） |
| `1` | `ar2_kernel`：partial 走 **F32**，逐位精确 |
| `2` | 同一个 kernel，**线上数据用 FP16**（每个 partial 先舍入到 FP16，求和仍是 F32、顺序 member0+member1） |

**为什么有收益**：该 all-reduce 是 PCIe/host 带宽受限；F32 → FP16 让线上字节减半，时间约减半。仓库自带测试可复现：

```bash
./build/ds4_gguf_test --ar 0 1 1614   # 1614 x 5120 ≈ 8.26M（1.6K prompt）
./build/ds4_gguf_test --ar 0 1 8192   # 8192 x 5120 = 41.9M（13K 每个 chunk）
```

| all-reduce | AR2=1（F32） | AR2=2（FP16 线上） |
|---|---:|---:|
| 8.26M | 8.7 ms | **4.5 ms** |
| 41.9M | 32.7 ms | **16.5 ms** |

实测（2026-11-01，2×2080Ti，experts 4，chunk 8192）：

| 指标 | AR2=1 | AR2=2 |
|---|---:|---:|
| 13K prefill | 665 | **730（+10%）** |
| 6.5K / 1.6K | 504 / 235 | **544 / 247** |
| decode（256 tok 中位） | ~41 | ~40（不受影响） |
| 10 题固定集 | 9/10 | **9/10**（9 题逐字一致；唯一差异是"要点数量"的第三条措辞，两版都因缺 `-`/编号判错，格式问题） |

**显存/内存：没有变化。**

- `G.arb.data` / `G.arb.pflags` 是 `hmap`（`cudaHostAllocMapped | Portable`）的 **pinned host RAM**，不是显存；AR2=1/2 分配同一块（chunk 8192、D 5120 时约 **670 MB**）；
- 显存里的专家槽/缓存计划由 `--reserve-mib`、`DS4_TP_SHARES`、模型大小决定，与 AR2 无关（本机 CUDA0 2263/15744、CUDA1 1879/15360，AR2=1/2 相同）；
- 唯一变化是 **PCIe 线上字节减半**。

**范围与回退：**

- 只影响 DeepSeek 的 TP2 **prefill**；decode 走另一条（`DS4_AR2_DECODE` 未开），不受影响；
- GLM、MiniMax、Qwen 的引擎不读这个 env；FP16 all-reduce 技术本身通用，但各家实现不同；
- 回退：`MAYA_DS4_AR2=1` + `./stop_ds4.sh && ./start_ds4.sh`；
- 对"逐位复现/极端精度"任务临时切回 `1`；
- 换 X99/x16 后重新 A/B：host 更快，相对收益约减半，但仍为正。

### 4.6 思考预算：`thinking_budget` 必须小于客户端 `max_tokens`

> 当前日常配置：`thinking_budget: 2048`（复杂任务可临时调回 4096）。

- 客户端的 `max_tokens` 是**总输出**（思考 + 答案），服务端的 `"thinking_budget"` 默认 **32768**。
- 两者相等时（客户端 `maxTokens: 32768` + 服务端默认 32768），模型可以把整个预算花在思考上，答案 0 token：

  ```
  done: 32768 tokens in 1113 s (29.8 tok/s) (length)   # 18.6 分钟，截断
  done: 32768 tokens in 1139 s (28.9 tok/s) (length)   # 19.0 分钟，截断
  ```

- 修复：配置里加 `"thinking_budget": 4096`。到 4K 服务端强制 `</think>`，答案在同一个 decode 里继续，最多约 100 秒思考。
- 客户端侧：`maxTokens` 保持 32768 即可（答案能拿到 ~28K）；`off` 档必须映射成字符串 `none`——映射成 `null`/省略时，服务端会当成"未指定"，回落到配置里的 `high`，思考并不会关。
- 经验：生成类任务（SVG、长代码）用 `low`（50）+ budget 4096；复杂推理用 `high`（75）+ budget 8192。

### 4.7 关键洞察

- 277GB 里 **161GB 是 Engram 表（常驻 SSD，每 token 读几 KB）**，真正驻留约 116GB；93GB 内存装不下 → 1,413 个专家读盘。
- **TP2 默认会退化成层切分**（`n_ff 2304` 无法按 256 值块二分），强制 5+4 后 prefill +29%。
- decode 是 **CPU lane + 内存带宽** 受限；prefill 是 **层内计算 + 两半区串行** 受限（copy lane 占墙钟 87%，但真正传输只占 26%）。
- 两卡显存不平衡（lead 104MiB 空闲 / 第二卡 1.5–2GB）是 TP 槽位取整 + head/草稿器归属决定的，所有调参尝试都失败（见 issue #734）。

## 4.8 2026-11-02 总体测试：chunk 与小开关都无正收益

在 AR2=2 的基础上，一次性配置了 `--prefill-chunk 16384`、`MAYA_DS4_AR2_DECODE=1`、`MAYA_DS4_DRAFT_COST=1`、`DS4_STREAM_ZC_ALL/NOWAIT=1`、`--reserve-mib 250`，逐项/组合实测：

| 配置 | 专家槽 | 13K prefill | decode | 质量 | 判定 |
|---|---|---:|---:|---:|---|
| AR2=2 基线（chunk 8192, reserve 300） | 2263/1879 | 730 | 39.6 | 9/10 | 基线 |
| chunk 16384 + 小开关 | 1694/1310 | **585** | 35.0 | 9/10 | ❌ 借走约 4GB 专家槽，−20% |
| chunk 8192 + 小开关组 | 2280/1896 | 700 | 36.0 | 9/10 | ❌ 小开关合计 −4~5% |
| **最终：AR2=2 + budget 2048** | 2263/1879 | **693**（同配置波动，最好 730） | **39.5** | **10/10** | ✅ 保留 |

结论：

- `chunk 16384` 的 prompt 缓冲借走约 4GB 专家槽（2263/1879→1694/1310），prefill 与 decode 双降；
- `AR2_DECODE=1`、`DRAFT_COST=1`、`ZC_ALL/NOWAIT=1`、`reserve 250` 合计 −4~5%，不保留；
- 最终配置：**AR2=2、chunk 8192、reserve 300、budget 2048**；
- **当前平台已经没有正收益的引擎参数可挖**，下一步只有 X99 的真 x16。

## 4.9 2026-11-02 长上下文 DSML 退化：服务端兜底解析（workbuddy 卡死）

### 现象

workbuddy 连接本地 DeepSeek 时，约 65K 上下文的会话做一半停住：`finish_reason=stop`，响应里没有 `tool_calls`。抓到的输出把 DSML 写成了残缺 XML：

| 正确 DSML | 65K 实际输出 |
|---|---|
| `｜DSML｜ invoke name="Bash"` | 整行丢失 |
| `｜DSML｜ parameter name="command" string="true"` | `<parameter name="command" string="true">` |
| `｜DSML｜ parameter`（闭合） | `</arg_value>` |
| `｜DSML｜ invoke`（闭合） | `</tool_call>` |

ASCII 部分保留、特殊 token 丢失，闭合标签退化成 Qwen 风格。服务端 `DsmlRewriter` 只认完整 DSML 块，解析失败后把残块当正文；客户端只认原生 `tool_calls`，于是"停住"。

### 根因

1. 引擎层：KV 的长期压缩 latent 是 **FP4**，近期窗口是 **FP8**（`maya-ds4` 的固定格式，没有 `--kv` 开关）；同轮 `--dspark on` 的 `draft_n:164 / accepted:117` 只是现象，投机解码会验证草稿，不能直接归因。65K 的格式退化更像 **IQ1_S 1-bit 权重 + 长上下文** 的共同作用。
2. 服务层：`DsmlRewriter` 没有容错，残缺块不产出 `tool_calls`。
3. 客户端：workbuddy 只接受原生 `tool_calls` 是正确行为，只能缓解，不能修复格式退化。

### 修复（本分支）

`serve/frontend.py` 的 `DsmlRewriter` 增加末端兜底：

- 内容流里出现裸 `<parameter name=...>`（没有 `｜DSML｜`）时，从该点起暂存，生成结束时尝试恢复；
- 接受 `</parameter>`、`</arg_value>`、`</tool_call>`、`</invoke>` 任一闭合；
- 工具名：优先用残存 wrapper（`<invoke name>` / `<function=>`）；没有则按参数名从请求的 tools schema 推断（如 `command` → `Bash`），推断不唯一就放弃；
- 只有整个暂存段是**一个完整调用**（参数名都能在某个 tool 里找到、调用后没有其他正文）才转换；否则原样输出；
- 正式 DSML、GLM/Qwen 形式、代码围栏/正文里的示例不受影响；
- 若暂存发生在 thinking 里，`close_reasoning()` 把它按 reasoning 原文吐出，不会误当工具调用。

新增 `serve/test_dsml_legacy.py`（16 项）：整段/逐字符流式、`string` 属性缺失、多参数与类型、wrapper、正常 DSML/Qwen 回归、未知参数/尾随正文/正文示例不转换、多个残块不合并、thinking 内不误判。

### 验证

- `python -m unittest serve.test_dsml_legacy serve.test_tools serve.test_ds41_conformance serve.test_responses_tools serve.test_minimax_frontend serve.test_stop` → 119 项通过（2 skip）；
- 重启后正常工具调用不受影响；
- 复现路径：同一个 65K 会话应能继续执行工具，而不是停在 `finish_reason=stop`。

### 后续（未做，属于权衡）

- 长上下文（>50K）关 DSpark：没有证据表明能改善格式（草稿会被验证），只会掉 decode；除非 A/B 看到质量差异，否则不做；
- KV 精度：DS4 引擎**没有** `--kv`/`--kv-cache` 选项；FP4 latent + FP8 窗口是引擎/模型格式，改成 8-bit 需要改 kernel 代码，不是配置项。按 256K 估算，一个会话的 KV 约 0.5GB（日志 `--parallel 2` 的第二个会话是 +0.51GB），8-bit 大约 +0.3–0.5GB 总量，不是 +2–3GB/卡；代价不大，但收益未被证明，暂不建议；
- 客户端：新会话 <20K、`reasoning.defaultEffort` 降到 medium；
- 根因是 **IQ1_S 权重 + 长上下文** 下的格式退化，KV FP4/投机解码的贡献未被单独证明；兜底让残块可用，但不等于消除退化。
